CloudFront VPC Origins 最小構成 検証レポート

検証日: 2026-06-02 ・ Region: ap-northeast-1 ・ AWS provider: hashicorp/aws v6.47.0
Sandbox: sandboxes/20260602-cloudfront-vpc-origin-minimal/01-ec2-minimal

TL;DR — VPC Origin 経由で疎通成立する最小は 8 リソース (VPC + IGW + subnet + SG + SG ingress rule + EC2 + VPC Origin + Distribution)。NAT GW / public subnet / EIP / ACM / Route53 / custom route table / custom NACL すべて 不要。 ただし VPC Block Public Access を ON にする場合は origin subnet 単位の exclusion 必須、custom NACL を当てるなら ingress/egress 共に ephemeral (1024-65535) の TCP 許可が要る (origin port は不要)。

2. デフォルトで良いもの一覧

VPC / EC2 / CloudFront それぞれに「これは 自分で作らなくて良い」項目が多い。検証で「default のままで疎通成立」を確認したもの:

項目default の中身本検証での扱い
Route table VPC default (main) route table。10.0.0.0/16 → local のみ default で OK custom RT 不要。IGW を attach してあっても route には載せない
Network ACL VPC default NACL。in/out 共に 0.0.0.0/0 を rule 100 で allow、最後に implicit deny default で OK custom NACL を当てるなら ephemeral allow が必要 (§5)
DHCP options set VPC 作成時に AWS default が紐付く default で OK
VPC tenancy default default で OK
EC2 IAM role 未付与 default で OK SSM 等使わないなら role 不要
EC2 EBS AMI 既定 (gp3 / 8GB 想定) default で OK
CloudFront viewer certificate cloudfront_default_certificate = true = *.cloudfront.net default で OK 独自ドメイン使わない限り ACM / Route53 不要
CloudFront cache policy AWS managed の Managed-CachingDisabled / Managed-CachingOptimized default で OK 検証では Managed-CachingDisabled を data で参照
CloudFront origin domain_name API 上は必須フィールドだが、vpc_origin_config 利用時は CloudFront が無視 default で OK placeholder.invalid 等を入れておけば動く
geo_restriction 制限なし (restriction_type = "none") default で OK
price class PriceClass_All 任意 検証では PriceClass_100 でコスト最小化。日本 edge は乗らない
VPC Block Public Access account / region 単位 off default で OK ON にする運用の場合は §4 参照
NAT Gateway / EIP / Public subnet — 不要 origin は private のまま、egress も不要
Route53 / ACM — 不要 CloudFront default cert + *.cloudfront.net で済む

3. Security Group ingress: 2 パターン

AWS Docs の prerequisite で 2 つの option が示されている。本検証では 両方とも疎通成立を確認:

optioningress source厳しさ備考
1 CloudFront managed prefix list com.amazonaws.global.cloudfront.origin-facing (pl-58a04531 @ ap-northeast-1) 緩 全 CloudFront edge IP を許可。VPC Origin 作成前から rule を入れられる
2 service-managed SG CloudFront-VPCOrigins-Service-SG (VPC Origin 作成時に自動生成) 厳 自分の Distribution 経由のみ許可。data "aws_security_group" + depends_on = [aws_cloudfront_vpc_origin.this] で取得

本検証の最終形は option 2 を採用:

data "aws_security_group" "cloudfront_vpc_origin_service" {
  filter {
    name   = "group-name"
    values = ["CloudFront-VPCOrigins-Service-SG"]
  }
  filter {
    name   = "vpc-id"
    values = [aws_vpc.this.id]
  }
  depends_on = [aws_cloudfront_vpc_origin.this]
}

resource "aws_vpc_security_group_ingress_rule" "origin_http" {
  security_group_id            = aws_security_group.origin.id
  ip_protocol                  = "tcp"
  from_port                    = 80
  to_port                      = 80
  referenced_security_group_id = data.aws_security_group.cloudfront_vpc_origin_service.id
}

4. VPC Block Public Access との関係

仮説「CloudFront → VPC Origin は IGW を経由しないので BPA に影響されない」は 外れ。AWS サポート公式回答: 実トラフィックは IGW を経由しないが、内部処理のため subnet 単位の BPA 許可 (exclusion) が必要。

BPA modeexclusion (mode = allow-bidirectional)curl 結果 (3 回)
off—HTTP 200, ~0.6s
block-bidirectionalなしHTTP 504, 30s timeout × 3
block-ingressなしHTTP 504, 30s timeout × 3
block-ingressVPC 単位HTTP 200, ~0.6s
block-ingresssubnet 単位 (origin subnet のみ)HTTP 200, ~0.6s
結論: 「アカウント全体に BPA を ON、VPC Origin を置く subnet だけ exclusion」が最小権限的な運用。VPC 全体を許可する必要はない。

5. NACL との関係

AWS Docs:

VPC origins ... NACLs: Subnet-level allow and deny rules are not evaluated for this traffic.

→ 実機では 評価される (deny-all NACL で 504)。詳細試験:

# ingress tcp 80 ingress tcp 1024-65535 egress tcp 80 egress tcp 1024-65535 curl
A————504
B✓———504
D✓——✓504
I—✓——504
J———✓504
H—✓—✓200 ← 最小
F✓✓—✓200
E✓✓✓✓200

最小 NACL allow set:

  • ingress tcp dst 1024-65535
  • egress tcp dst 1024-65535

origin port (80 / 443) は ingress / egress 共に 不要。

考察 (実機 ENI 配置から):

  • CloudFront 管理 ENI (InterfaceType: cloudfront_managed) と EC2 ENI は 同じ subnet にいる
  • subnet 内 hop (CF ENI ↔ EC2 ENI, dst port 80) の packet は NACL に当たらない
  • NACL に当たるのは CF ENI ↔ 外部 CloudFront edge plane の internal protocol。両側 ephemeral port を使う模様
  • よって request の dst port 80 すら NACL ingress には不要

6. ALB origin + 2 AZ の場合の差分

本番運用想定で ALB + 2 AZ private subnet 構成も別 approach (02-alb-2az/) で実機検証。

構成差分

項目01 (EC2 直 origin)02 (ALB origin + 2 AZ)
subnet 数12 (ALB の HA 要件、別 AZ)
SG 段数1 段 (CF service SG → EC2)2 段 (CF service SG → ALB → EC2)
terraform リソース数816
VPC Origin が指す対象EC2 ARNALB ARN
CloudFront 管理 ENI1 個 (origin subnet)2 個 (両 AZ subnet に 1 個ずつ)
apply 所要時間約 12 分約 15 分 (ALB 3 分追加)

BPA exclusion の挙動 (subnet 単位試験)

BPA modeexclusion subnet aexclusion subnet bcurl
off——200 (baseline)
block-ingress——504 (4/4)
block-ingress✓—200 (6/6)
block-ingress—✓200 (6/6)
block-ingress✓✓200 (4/4)
発見: 2 AZ ALB 構成では 片方の subnet だけ exclusion すれば疎通成立。CloudFront edge が許可された CF ENI を選択して使う模様 (failover 的挙動)。
ただし運用上は 両 subnet exclusion を推奨 (片 AZ 障害時の through-traffic 維持のため)。

NACL の挙動

両 subnet に同一 custom NACL を associate して試験 → 01-ec2-minimal と 同じ 結論:

  • deny-all (rule なし) → 504
  • ingress tcp 1024-65535 + egress tcp 1024-65535 のみ → 200

origin port (80 / 443) は ingress / egress どちらにも不要、という結論は ALB origin / 2 AZ でも変わらない。
